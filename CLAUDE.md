# StudyBuddy AI

An AI-powered study companion featuring **Explain**, **Summarize**, **Quiz Generator**, **Flashcard Creator**, an **All-in-One Studio**, a **Real-Time Streaming AI Chatbot**, and **Document RAG** (upload your notes). Any tool can be grounded in the uploaded documents via an optional `document_ids` field and the shared **My documents** picker (`DocumentPicker`). The standalone **Ask My Docs** page (`/rag`) was retired once every tool grounded itself from the same selection; the `/api/rag/*` endpoints remain.

## Tech Stack
- **Frontend:** React, Tailwind CSS, React Query
- **Backend:** Django, Django REST Framework
- **LLM Integration:** LangChain (`langchain-groq` + Groq API `openai/gpt-oss-120b`) — all text, JSON, streaming, and structured output
- **RAG:** Gemini Embedding 2 (`gemini-embedding-2`) for embeddings + Groq for grounded answers; pgvector retrieval with automatic numpy cosine-similarity fallback
- **URL scraping:** Firecrawl when `FIRECRAWL_API_KEY` is set, otherwise the built-in requests/BeautifulSoup scraper — SSRF-guarded in both cases
- **Database:** PostgreSQL (via Neon)
- **Deployment:** Render (Backend), Vercel (Frontend)

## Architecture Pointers
- **API Surface:** the frontend uses explicit resource-based endpoints in `backend/study_api/urls.py` (e.g., `POST /api/generate/`, `GET /api/sessions/`). The RAG upload uses the multipart `POST /api/rag/upload/`.
- **System prompts:** the tool prompts (`EXPLAIN_SYSTEM`, `SUMMARIZE_SYSTEM`, `QUIZ_SYSTEM`, `FLASHCARDS_SYSTEM`, `CHAT_SYSTEM`) live in `views.py`; `CHAT_SUGGESTIONS_SYSTEM` is the one exception, in `dispatchers.py`.
- **LLM calls** all go through `langchain_client.py`. Structured calls use JSON prompting with `JsonOutputParser` validated against the Pydantic schemas in `schemas.py` — not native tool-calling, so they work on models without tool support. `build_message_history()` keeps inbound roles intact, but Groq accepts a system message only in first position, so any `role: "system"` turn in the client's history is folded into the single leading `SystemMessage` instead of appended — that is why `ChatMessageSerializer.role` allows `"system"` (the Study Chat page sends the user's other session titles as one) while only `user`/`assistant` turns are ever persisted.
- **RAG** lives in `rag_pipeline.py`: extract → chunk → embed → retrieve → answer. Ingestion runs in a background thread; clients poll via the `getDocumentStatus` helper in the frontend. Changing `RAG_EMBED_MODEL` or `RAG_EMBED_DIMENSIONS` requires re-indexing every uploaded document. Answers are plain text (no markdown) — the frontend renders them with `whitespace-pre-wrap`, so raw `**`/`##` shows up literally.
- **Document grounding is one shared path, not six per-tool variants.** `views.py`'s `_ground_documents(user, document_ids, query)` is the only entry point: it filters the requested IDs through `dispatchers.ready_document_ids(user, requested)` (ownership + `status='ready'`), retrieves once, and returns either a `{context, sources, document_titles}` dict (context built by `rag_pipeline._build_rag_context()`) or an error `Response`. `GenerateView.post` calls it once before dispatching and passes the resulting `docs` into the existing response builders (`_explain_response`, `_quiz_response`, `_chat_reply_response`, …), so retrieval happens per request rather than per tool type; `ChatStreamView.post` calls it before the generator starts and **returns the error Response instead of streaming**, because a stream that has already sent headers cannot fail cleanly. Grounded excerpts join the prompt inside `_with_docs()` *before* `_cached_json_response` computes its key (`prefix + md5(user_msg)` at [views.py:208](file:///E:/studybuddy-langchain/backend/study_api/views.py#L208)), so the response cache is document-set aware — a different selection can never replay another library's answer. `_with_docs()` also adds the abstain instruction (`DOCS_PREAMBLE` in `views.py`), and `_grounded_chat_system()` is its chat-shaped counterpart. Sources are merged into the payload **before** `cache.set`, so reopened history still shows which documents answered it. On the frontend the panel is `DocumentPicker` and `DocumentSources` in `src/components/shared/`, backed by the `useDocumentLibrary()` hook and `docIdsOption()` helper in `src/components/shared/documentLibrary.js`, plus `GroundingNote.jsx` for the conditional "the output will be based on the selected documents" line under a page's input. Every page reads the **same** library instance through `useLibrary()` (`src/context/DocumentLibraryContext.jsx`), which mounts `useDocumentLibrary()` once app-wide and persists the picked IDs to `localStorage` (`studybuddy.selectedDocumentIds`) — so a selection made on Explain is the selection Quiz grounds in; never keep a second per-page copy of it. Every tool page mounts the same pieces, so a new tool gets grounding by reusing them rather than writing library state again.
- **URL gate:** `content_fetcher.py`'s `process_topic_with_url()` is the single place that decides whether input gets scraped — only URL-type topics are fetched; plain-text topics go straight to Groq.
- **The home route has two faces.** `pages/HomePage.jsx` renders `components/home/HomeLanding.jsx` for guests and `Layout` + `components/home/HomeDashboard.jsx` for signed-in users, with a spinner while `useAuth().loading` so a signed-in reload never flashes the landing. The dashboard reads only existing endpoints — `["generations"]` and `["rag_documents"]` reuse the same react-query keys as AllPage and the document library, alongside new `["chat_sessions"]` and `["usage_stats"]` (the first consumer of `GET /api/usage/`) — and derives everything else (streak, 14-day series, tool mix, checklist, next steps) from pure functions in `src/utils/personalize.js`, each taking `(rows, now)` with an injected clock and covered by `personalize.test.js`; never compute these metrics inline in JSX, and never render a number the API did not supply. The signed-in hero focus box and the landing's "try the router" demo both call the same `routeIntent()` from that module. The pre-fill hand-off is `stashPendingTopic()` / `usePendingTopic(setter)` in `src/utils/pendingTopic.js`: consumption must stay in an effect, because StrictMode double-invokes `useState` initializers in dev and a read-once delete inside an initializer silently eats the value. `queryFn: listGenerations` must stay wrapped (`() => listGenerations()`) — react-query otherwise passes its context object as the `type` filter.
- **Usage tracking:** `GenerateView.post` calls `langchain_client.reset_last_usage()` before dispatching to a tool core and `take_last_usage()` immediately after a 200 (the ContextVar is cleared on read, so it must be taken once per call), then persists `Generation.input_tokens` / `output_tokens` / `cost`, priced by `estimate_cost_usd()` from `settings.GROQ_PRICE_PER_M_INPUT` / `_OUTPUT` — both default to 0, so an unconfigured deployment records an honest zero rather than a guessed rate. Do **not** also insert a `UsageLog` row for the same call: `_action_usage_stats` sums Generation and UsageLog together, so writing both double-counts. Streamed chat creates no `Generation`, so `ChatStreamView` writes the turn's `UsageLog` row itself from the same `take_last_usage()` read once the stream ends — that row is what makes chat spend count against the daily budget. On a response-cache hit the recorded counts are `0 / 0`, which is correct — no provider call happened; that is why `reset_last_usage()` exists, since `--noreload` dev servers reuse worker threads. `query_groq_structured` (quiz, flashcards) overwrites the ContextVar when the tool-calling attempt falls through to JSON prompting, so those rows carry the successful call's tokens only — an undercount, never an overcount. `test_usage_tracking.py` asserts the persisted row and the cache-hit zeros, not just the helpers.
- **Daily token budget:** `settings.USER_TOKEN_LIMIT` (default 10,000; `0` disables it) caps each account's per-day token spend. `dispatchers.tokens_used_today(user)` sums the day's `Generation` and `UsageLog` tokens via `created_at__date=timezone.localdate()` (`TIME_ZONE='UTC'` is now set explicitly in `settings.py`; while it was unset Django's `America/Chicago` default decided the day boundary, so the budget reset near 19:00 UTC while the 429 message promised midnight), and `enforce_daily_token_limit(user)` returns either a 429 `Response` with a plain-language message or `None`. `GenerateView.post` and `ChatStreamView.post` call it **before** any model call — a request can overshoot by at most one call, since a call's cost is unknown until it runs. `GET /api/usage/` additionally returns `daily_token_limit`, `tokens_used_today` and `tokens_remaining_today`, which `HomeDashboard.jsx` renders as a meter (amber near the cap, rose when spent). Never enforce it after the LLM call, and never meter a route the dashboard does not report. `ChatStreamView.event_generator` records usage and the partial reply in a `finally`, not in the success path, because a disconnecting reader makes WSGI throw `GeneratorExit` at the `yield` — a `BaseException`, so the `except Exception` handler never sees it and the turn would otherwise be spent but unmetered.
- **Signed-in identity:** the access token embeds `username` — `UsernameTokenObtainPairSerializer` in `serializers.py`, wired into the login route in `urls.py`; simplejwt copies custom claims through refresh rotation, so a silent renewal keeps the handle. `AuthContext` decodes the payload locally and, when a token predates the claim, recovers the name from `GET /api/auth/me/` (`MeView`). Do not add a hardcoded display name anywhere: `Layout`'s `|| "Student"` exists only to cover the few hundred milliseconds before that recovery call resolves.
- **Signup notification email:** `signals.notify_on_signup` listens on `post_save` for every created `User`, and `send_signup_notification()` returns immediately when `settings.SIGNUP_NOTIFICATION_EMAIL` is empty — the feature is config-gated, not flag-gated, so setting that one value activates it. Delivery failures are swallowed with `logger.exception` so a bad SMTP config can never turn a successful signup into a 500. Because the signal fires on **any** created user row, a live script that provisions an account sends real mail the moment the recipient is set: stub `study_api.signup_notifications.send_mail`, or override `EMAIL_BACKEND` with the console backend, in every ad-hoc script. Gmail requires a 16-character App Password (not the account password) and `DEFAULT_FROM_EMAIL` equal to `EMAIL_HOST_USER`, or the send is rejected. The send is **inline in the signup request**, and that is its cost: measured 5.2 s for one notification (3.3 s of it TCP + STARTTLS + AUTH), which is why a live signup POST takes 6.1 s against 1.2 s for the same request with the recipient unset. `EMAIL_TIMEOUT` (5 s default) is what bounds an unresponsive host — without it `smtplib` blocks on the OS TCP timeout, measured at 21 s on Windows and long enough on Linux for gunicorn's `--timeout 120` to kill the worker. Keep the notification best-effort: never let it change a signup's status code. On Render's **free** tier it cannot deliver at all — outbound SMTP ports 25/465/587 are blocked by the platform — so deployed signup mail is a known, accepted limitation, not a bug to chase; locally the same code path is verified working. A failed send still leaves a trace: with no `LOGGING` block in `settings.py`, `logging.lastResort` prints `Could not send signup notification for user …` and the traceback to stderr (Render's log stream), so the *absence* of that line is what tells you `SIGNUP_NOTIFICATION_EMAIL` is empty.
- **Response cache:** `_cached_json_response` in `views.py` is the only cache site (one `cache.get` / one `cache.set`), wrapping just the four JSON tools — `explain`, `summarize`, `quiz`, `flashcards` — for 7 days (Django `DatabaseCache` on the `studybuddy_cache` table, key = tool prefix + md5 of the fully-expanded prompt including fetched web content **and any grounded document excerpts**, which is what keeps the cache document-set aware). Chat and RAG queries are never cached, and failed LLM calls are never cached.
- **Throttle scopes:** `throttles.py` defines `StudyBuddyAnonRateThrottle` (60/hour), `StudyBuddyUserRateThrottle` (300/hour) and `ActionRateThrottle`, which reads a per-scope ceiling from `DEFAULT_THROTTLE_RATES` — `generate` 60/hour, `rag` 40/hour, `chat` 90/hour — for views that set `throttle_scope`. Expensive views therefore trip before the global user ceiling; list and status endpoints stay on the loose global bucket. Anonymous callers cannot be proven non-throttled on a JWT-only endpoint, because `APIView.initial()` runs permissions before throttles, so 401 arrives first.
- **SSRF guard:** `content_fetcher.py` blocks internal targets at two layers — `_host_is_public()` resolves the hostname and requires every DNS answer to be a global IP (defeats DNS rebinding, encoded IPs, cloud metadata), and `_safe_get()` follows redirects manually (max 3 hops, `MAX_REDIRECTS`), re-running `_is_safe_url` + `_host_is_public` on every hop before connecting. Never reintroduce `allow_redirects=True` on user-supplied URLs. A third, optional gate sits inside `_is_safe_url`: `settings.ALLOWED_SCRAPE_DOMAINS` (comma-separated, suffix-matched by `_hostname_allowed()`) restricts scraping to listed domains when non-empty, and defaults to `""`, meaning no extra restriction.

## Development Workflow

### Frontend
- **Location:** `./frontend/`
- **Commands:**
  - `npm start` — development server
  - `npm test` — Jest suite (71 tests in 7 files: `src/utils/api.test.js` (19), `src/utils/personalize.test.js` (31), `src/context/AuthContext.test.jsx` (7), `src/components/shared/documentLibrary.test.jsx` (4), plus `Button`/`Card`/`Input` render tests)
  - `npm run build` — build for production
- **Notes:** CSS is managed in `src/index.css`. New components should follow the established pattern (Input, Select, Button) located in `src/components/`, and anything two pages already need belongs in `src/components/shared/` — the document-grounding panel (`DocumentPicker`, `DocumentSources`, `GroundingNote`, `useDocumentLibrary`) is the current example, mounted by all six pages that touch documents (Explain, Summarize, Quiz, Flashcards, Chat, All — the standalone RAG page was retired) — rather than reimplemented per page. Two client-state rules apply everywhere: a request a page no longer needs is **aborted** (`shared/generationAbort.js` gives each tool page one controller and aborts on unmount, `ChatPage` holds its own for the SSE stream, and an `AbortError` must never reach the user as an error toast or as a completed reply), and anything owned by the signed-in account is **torn down when the token is lost** (`AuthProvider` clears the `QueryClient`, `useDocumentLibrary` drops the stored document selection) — React Query caches by key, not by account. A mutation that moves a dashboard number has to invalidate the key `HomeDashboard` reads: those queries run with `staleTime: 60000`, and returning to `/` inside that window serves the cache, so nothing refreshes unless the page that made the change says so. One error-surfacing rule: an auth endpoint answers an invalid payload with DRF's field-error dict (`{"email": ["Enter a valid email address."]}`), and `rejectionMessage()` in `AuthContext` reads whichever key the server used — a mapping that looks only at `detail`, or only at one field, silently turns the server's real reason into "Registration failed".

### Backend
- **Location:** `./backend/`
- **Setup:**
  - `python -m venv venv`
  - `source venv/bin/activate` (or `venv\Scripts\activate` on Windows)
  - `pip install -r requirements-dev.txt` (runtime deps live in `requirements.txt`, which `build.sh` installs alone on Render)
- **Commands:**
  - `python manage.py runserver` — start dev server. Locally it is always launched with `--noreload`, so an edit never reaches an already-running server: restart it (or start one on a throwaway port) before judging a backend change through HTTP.
  - `pytest` — run the 138-test suite (auto-switches to SQLite; no real database needed, and `test_retrieve_chunks_uses_pgvector_when_available` skips there). RAG and grounding share `test_rag.py` (47 tests) and `test_generations.py` (15) — 62 of the 138 between them. CI also runs a Postgres + pgvector job that sets `TEST_DATABASE_URL` so the raw vector SQL executes somewhere it can.
  - `ruff check backend/` — lint (the CI gate)
  - `uvx pyrefly check --min-severity warn` — type check; warnings are hidden at the default severity. Configs: `pyrefly.toml` (root + backend) and `pyrightconfig.json`.
- **Environment:** `.env` file with `GROQ_API_KEY`, `GROQ_MODEL`, `GEMINI_API_KEY`, `DATABASE_URL`, `SECRET_KEY`; optional `FIRECRAWL_API_KEY`, `ALLOWED_SCRAPE_DOMAINS`, `RAG_*` tunables, `USER_TOKEN_LIMIT`, `DB_SSL_REQUIRE`, the `THROTTLE_*_RATE` ceilings (`anon`/`user`/`generate`/`rag`/`chat`), and signup-email vars. The README has the full template.

## Guidelines for Claude
- **Code Style:** Follow existing patterns. Use Tailwind classes as configured in `tailwind.config.js`. Match comment density of existing files.
- **Components:** Reuse existing shared components (`Button`, `Card`, `Input`, `Select`, `PageHeader`) rather than creating raw elements where possible.
- **AI/LLM Changes:** Prompts live in `views.py` (see the System prompts pointer above), LangChain logic in `langchain_client.py`. Changes require strict verification of structured output against the Pydantic schemas (Quiz & Flashcards use `JsonOutputParser` with JSON prompting) and of SSE frame formats (`{"chunk"}`, `{"done"}`, `{"error"}`) for streaming.
- **Scraping Changes:** Keep the URL gate in `process_topic_with_url()` intact — non-URL topics must never reach Firecrawl or direct scraping. Preserve the SSRF guard: every redirect hop must pass both `_is_safe_url` and `_host_is_public` before connecting. Keep the `ALLOWED_SCRAPE_DOMAINS` check inside `_is_safe_url` rather than only on the first URL, so each hop is re-validated against the allowlist. Tests mock `requests` and `_host_is_public` rather than hitting the network or DNS.
- **RAG Changes:** If you touch the embedding model or dimensions, flag the re-indexing requirement. Keep the pgvector path and the numpy fallback behaviorally identical. The pgvector branch only executes in CI's `RAG pgvector SQL` job (Postgres service + `TEST_DATABASE_URL`) because it falls back silently to numpy everywhere else — so after editing `_retrieve_pgvector()`'s SQL, expect a local run to skip it and check that job instead. Grounding must stay a property of the request, not of the tool: new tools and new pages opt in through `document_ids` + `_ground_documents()` and `DocumentPicker`, so never add a per-tool copy of the retrieval or authorization logic, and never let a grounding failure degrade into an ungrounded answer — return the error (or, in a stream, before the first frame).
- **Cost & limit changes:** any route that reaches a model must call `enforce_daily_token_limit(request.user)` **before** the call and record its usage afterwards (`Generation` row, or a `UsageLog` row for a stream) — a new unmetered route silently spends the provider quota outside the budget. Keep the refusal a 429 with a plain-language message, and never meter after the response. Log every failure you turn into a 5xx: `views.py` and `dispatchers.py` call `logger.exception` at each conversion site, because a *handled* exception never reaches Sentry and a Groq outage or rate-limit storm would leave no server-side trace — include the tool prefix or user id, never the prompt text.
- **Request-duration changes:** `render.yaml` runs gunicorn with `--timeout 120 --threads 4` (gunicorn's own default is a 30s sync worker). `FIRECRAWL_TIMEOUT` is 60s and scraping happens **before** the LLM call, so any route allowed to run longer must raise that timeout in step, or the worker is killed mid-request and the client gets a bare 502.
- **Settings defaults:** make them fail safe and env-overridable, never inferred from an unrelated flag. `DEBUG` is off unless the env turns it on (local `.env` sets `DEBUG=True`), and Postgres TLS is its own `DB_SSL_REQUIRE` switch instead of a by-product of `DEBUG` — on for any Postgres URL, never applied to sqlite because its driver rejects connection `OPTIONS`. Note that `_env_bool()` reads a present-but-empty value as false, so an env template must leave such keys commented, not blank.
- **Response cache:** `_cached_json_response()` keys on the prompt text **plus** the grounded `document_id`s, because a cached payload embeds the owner's sources and titles. Any new cached response that carries user-owned identifiers must fold them into the key, or two accounts that upload the same file replay each other's provenance; ungrounded prompts stay shared across accounts, since that dedup is what saves provider money.
- **Build:** Always verify `npm run build` succeeds after frontend changes affecting CSS or bundling.
- **Documented figures:** README.md ("By the numbers") and CLAUDE.md quote live values — test counts, endpoint count, configured limits — and must be updated in the same commit that changes the thing they describe. Never add a speedup or accuracy percentage for LangChain, RAG, or caching to the README unless it comes from a benchmark actually recorded in the repo; there is no before/after baseline, and the cache, retrieval, and build numbers are reproducible measurements instead.
